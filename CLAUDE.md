# CLAUDE.md

Loom is a self-hosted, single-user web app for tracking projects, studies,
and ideas as a connected graph - built to fight context-switching overload
when juggling many parallel projects, courses, and half-formed ideas at
once. One graph per account; no collaboration features.

## Stack

- **Backend:** Rust, Axum, `sqlx` (compile-time-checked queries, no ORM),
  Postgres.
- **Frontend:** SvelteKit + TypeScript, `@xyflow/svelte` for the canvas
  view, `adapter-static` served by its own nginx container.
- **Types:** `ts-rs` generates the frontend's TypeScript types from the
  Rust request/response structs - one source of truth for the API
  contract.
- **Auth:** Password + Argon2id, short-lived JWT access token, rotated
  refresh token in an httpOnly `Secure` cookie, rate-limited auth
  endpoints.
- **Deployment:** three Docker Compose services (backend, frontend,
  database), images published to GHCR. Meant to sit behind a host nginx
  that already terminates TLS.

## Repo layout

- `backend/src/handlers/` - parse/validate requests, map errors, call
  into `repo/`. Thin; no `sqlx` calls here.
- `backend/src/repo/` - the only place that touches `sqlx` directly.
  Every function takes `user_id` as its first argument.
- `backend/src/models/` - request/response structs, `TS`-derived.
- `backend/src/auth/` - password hashing, JWT, refresh-token rotation.
- `backend/src/middleware/` - the `AuthUser` extractor that pulls
  `user_id` off the verified JWT.
- `backend/migrations/` - one file per change, run automatically on
  boot via `sqlx::migrate!`.
- `frontend/src/lib/api/` - HTTP client and endpoint wrappers, including
  single-flight token refresh.
- `frontend/src/lib/graph/` - display, filtering, grouping, layout,
  ordering, and timeline logic for the board views (each with a spec
  file).
- `frontend/src/lib/stores/` - graph cache, session, prefs, filters, ui,
  toasts.
- `frontend/src/lib/components/` - Svelte components, including
  `detail/` (the node slide-over) and `ui/` (design-system primitives).
- `frontend/src/lib/types/` - generated by `ts-rs`; gitignored, never
  hand-edited.
- `.github/workflows/` - `test.yml` (runs on PRs and is called by
  `release.yml`), `release.yml` (builds/pushes GHCR images on pushes to
  `master` and `v*` tags, drafts a GitHub release on tags).

## Domain model & terminology

- **Node kinds:** `idea` (uncommitted capture, no progress or
  checklist), `project` (the only kind with a checklist), `study`
  (courses/books/topics - the only kind with a tracked
  `progress_current`/`total`/`unit` counter), `path` (the only
  container kind - other nodes join it via `part_of`; paths can nest).
- **Promote:** changing a node's `kind` in place (same row, same id,
  same edges) rather than recreating it. Changing kind drops data the
  new kind can't hold (e.g. leaving `project` deletes its checklist).
- **Backlog:** any node with `status = idea`, regardless of kind.
- **Focus tier:** `primary` / `secondary` / `background` - orthogonal
  to status, drives what surfaces on the dashboard.
- **Blocked:** derived, never stored - a node with an unmet `requires`
  edge to a non-`done` node.
- **Container progress:** derived from the done/not-done ratio of a
  path's `part_of` children. **Checklist progress:** derived from a
  project's checklist items. Both distinct from a study's own tracked
  counter.
- **Poke:** an append-only "I worked on this" log entry, decoupled from
  `updated_at`. **Last touched** = `MAX(poked_at)`, derived.
- **Active period:** a `started_at -> ended_at` span of a node being
  worked on (`ended_at` null = ongoing). The first one opens on first
  activation; with "Track active periods" on, pausing/archiving closes it
  and reactivating opens a new one. **Started** = the first period's start
  and **Completed** = the last period's end while `done` - both derived,
  never stored; editing them moves those period edges.
- **Stale:** an active/queued node whose last poke (or creation date)
  is more than 14 days old.
- **Accent:** the user-assigned node color.
- **Edges:** `requires` (hard, blocking - cycles rejected), `part_of`
  (child -> its path, cycles rejected, one path per node), `related`
  (soft, cycles allowed). Always directed forward from the node being
  edited.

## Core rules

- Every node/edge/topic/poke/checklist query is scoped by `user_id`,
  extracted once via middleware from the verified JWT. Repository-layer
  functions take `user_id` first, always - this is the actual security
  model (no roles/permissions system exists).
- Derived state (`blocked`, container/checklist progress, last-touched,
  started/completed) is computed at query time, never written to a column.
- Kind capabilities are enforced in both the handlers (400s) and DB
  constraints - don't relax one without the other.
- Never edit an applied migration; add a new one.
- After changing a query, run `cargo sqlx prepare` in `backend/` and
  commit the updated `.sqlx/` cache - CI builds offline from it.
- `ts-rs` types are regenerated (`npm run types` in `frontend/`), never
  hand-written. If a type is missing on the frontend, add `#[derive(TS)]`
  on the backend struct, don't redeclare it.
- The frontend graph store refetches the whole graph after any
  mutation, since derived state can change on other nodes.

## Code conventions

- Descriptive, meaningful names everywhere - no single-letter variables
  except genuine loop counters with no broader meaning.
- Rust: standard `rustfmt`/`clippy`-clean, `snake_case`.
- TypeScript: standard `camelCase` - don't force Rust naming style across
  the API boundary.

## Testing

Auth flows and ownership-scoping are the security-critical paths - these
need real test coverage, not just happy-path manual checks. Everything
else can be tested more loosely.

Backend tests (`backend/tests/*.rs`) use `#[sqlx::test]` and need a live
`DATABASE_URL`. Frontend tests are Vitest specs alongside the modules
they cover (`*.spec.ts`).

If anything is architecturally ambiguous, ask rather than guessing.

## Running the project

**Locally** (backend and frontend as separate processes, hot-reloading):

```sh
docker compose up -d database   # just the database
cd backend && cargo run         # needs .env with DB_HOST=localhost
cd frontend && npm run dev      # proxies /api to :8080, serves on :5173
```

**Via Compose** (production-shaped, three containers):

```sh
cp .env.example .env   # first time only
docker compose up --build   # frontend on :8081, API on :8080
```

**Tests:**

```sh
cd backend && cargo test          # needs DATABASE_URL (live Postgres)
cd frontend && npm run check      # type-check
cd frontend && npm test           # vitest
```
